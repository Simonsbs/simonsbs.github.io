## 1. Enterprise knowledge assistant and evaluation lab

**Customer scenario:** A support team needs answers from product documentation and internal procedures, with a way to check the source of each answer.

**Build:** A React interface over the existing Python/LangChain approach, with document ingestion, retrieval and local inference through Ollama. Use a small synthetic document pack with intentionally conflicting, outdated and access-restricted documents. Add citations, an “insufficient evidence” response and a view of the retrieved passages.

**Make it inspectable:** Create a labelled set of 30 to 50 questions covering supported answers, missing information, conflicting sources and access boundaries. Report actual retrieval results, groundedness checks, latency and token usage from recorded runs. Show which checks are automated and which use human review. Microsoft’s [RAG evaluation documentation](https://learn.microsoft.com/en-us/azure/foundry/concepts/evaluation-evaluators/rag-evaluators) provides a useful distinction between retrieval quality and answer quality.

**A five-minute demonstration:** Ask a straightforward question, inspect the evidence, ask an unanswerable question, switch retrieval settings, and compare the results against the labelled set.

**Implementation status, 11 November 2026:** The standalone application is public at [knowledge.bestdev.co.il](https://knowledge.bestdev.co.il/), with 12 synthetic documents, 26 passages, 40 development questions and 28 verification questions. It includes ingestion/import, source inspection, role-filter simulations and six retrieval configurations for each set. Governed retrieval at three passages has 100% labelled evidence recall and 100% decision accuracy on both finite sets. Q12 and Q13 are fixed through English inflection normalization; a vocabulary guard prevents an unsupported storage question from becoming an answer. Setup and decisions are in [the project README](https://github.com/Simonsbs/knowledge-assistant-lab). The portfolio is already published and links externally.

**Live inference status:** Ollama 0.40.16 is installed. The validated default is now `qwen3:8b`, after semantic inspection found a persistent permission error in the smaller model. The complete run passes 68/68 pipeline cases, all 46 generated-answer content checks and all seven context-rejection probes. Each accepted answer has a source-by-source agent review. Recorded warm median generation was 640 ms and p95 was 1,032 ms on the RTX 3070; the initial cold Qwen request took about 22.6 seconds. The 14 Node tests, 19 Python tests and build pass. See [live validation](https://github.com/Simonsbs/knowledge-assistant-lab/blob/main/docs/validation/knowledge-lab-live.md) and the [answer comparison](https://knowledge.bestdev.co.il/data/semantic-review.html).

**Version 1 completion and scope:** Simon accepted the completed agent validation on 11 November 2026. Project 1 is complete for that agreed release scope. Project 2 was started after that acceptance and is now also validated and public. Both question sets are agent-authored regression fixtures, not an independent human benchmark. Human review was not performed or claimed. Browser roles simulate filtering over public synthetic data; the local adapter independently admits canonical context for its configured role. This demonstrator remains separate from the documented PoC and production case studies.

## 2. Integration and webhook reliability lab

**Customer scenario:** An operational platform needs reliable updates from external systems, including when events arrive twice, out of order or during an outage.

**Build:** ASP.NET Core endpoints, SQL Server or a documented local substitute, and a React operations console. Include signed test events, a receiver, an event log, idempotency keys, retry policies, a dead-letter queue and replay controls. Keep the data synthetic and make failure injection a visible part of the interface.

**Make it inspectable:** Tests for invalid signatures, expired credentials, duplicate delivery, malformed payloads, temporary outages and successful replay. Include correlation IDs, structured logs and a short runbook. Measure the results of the actual test runs rather than inventing throughput or uptime claims.

**A five-minute demonstration:** Submit an event, submit it again, introduce a receiver outage, inspect the retry history, restore the receiver and replay a failed event.

**Version 1 completion, 11 November 2026:** The standalone application is public without sign-in at [integration.bestdev.co.il](https://integration.bestdev.co.il/), with its own [repository](https://github.com/Simonsbs/integration-reliability-lab) and local folder `D:\Projects\integration-reliability-lab`. The React console uses a runnable ASP.NET Core 10 API with SQLite locally, and a Cloudflare Worker with D1 on the public host. Both implement the same HTTP contract. The public host does not run ASP.NET Core. HMAC checks, HTTP deliveries, persisted receipts, optimistic concurrency, order-version handling, retries, dead letters, replay, audit and evidence export are implemented. Retry time advances through an explicit virtual clock and the browser initiates deliveries.

**Recorded validation:** All 14 unit checks pass. The same 25 HTTP scenarios pass against ASP.NET Core, local Worker/D1 and the public custom domain, with 216 actual requests in each final run. Both runtimes pass actual capability-expiry and process-restart checks. Public D1 data and duplicate receipts survived deployment. Six public hosting checks, desktop/mobile browser checks and Windows/Linux CI pass. The original static-header failure and its correction are retained in the [validation evidence](https://github.com/Simonsbs/integration-reliability-lab/blob/main/VALIDATION.md). Architecture, decisions and the runbook are published with the source. Site version 4 deploys commit `c7a36615f11cfe9d92aac36d991e6fe4b0236659`. The published portfolio includes Integration Lab on Home and Projects, with a dedicated project page and separate live/source links. Project 3 was started after this release and is now also complete.

**Scope boundary:** The demo illustrates reliability and integration patterns. The public build is separate from customer systems. AWS’s [operational excellence guidance](https://docs.aws.amazon.com/wellarchitected/latest/framework/oe-design-principles.html) is a useful review reference for observability and safe operational changes.

## 3. Technical presales solution workbench

**Customer scenario:** A business has disconnected systems and several possible modernisation routes. The technical seller needs to make the choices understandable and testable.

**Build:** A guided discovery brief covering business goals, current systems, integration requirements, non-functional requirements, constraints and stakeholders. Compare two or three architecture options. Produce an editable solution outline, diagram, assumptions, risks, implementation phases and PoC success criteria.

**Make it inspectable:** Include three clearly fictional customer scenarios and explain why each recommendation follows from its inputs. Any cost comparison should use explicit user-supplied assumptions and show the calculation. Add an architecture decision record for a rejected option. An AI drafting layer can follow after a useful deterministic version exists.

**A five-minute demonstration:** Walk through discovery, reveal a new constraint, explain how it changes the design, and export the updated proposal and PoC plan.

**Version 1 completion, 11 November 2026:** The standalone workbench is public without sign-in at [presales.bestdev.co.il](https://presales.bestdev.co.il/), with its own [repository](https://github.com/Simonsbs/presales-solution-workbench) and folder `D:\Projects\presales-solution-workbench`. It implements guided discovery, three provider-neutral architecture blueprints, hard constraints before weighted scores, editable cost assumptions with reconciling line items, pinned before/after comparisons, preserved author wording with revision-review flags, a conceptual diagram, proposed decision records, implementation phases and six measurable PoC acceptance criteria. The seven-file proposal ZIP includes an editable JSON brief, Markdown proposal, SVG diagram, CSV PoC plan, decision record, analysis and README. All scenario names, ratings, rates and timing allowances are fictional planning assumptions. Drafts and exports stay in the visitor's browser; the public Worker is read-only.

**Recorded validation:** All 48 unit tests and 12 scenario/export checks pass, including six baseline/changed-constraint decisions, independent cost totals, budget boundaries, actual ZIP extraction, safe text handling and persistence recovery. Fourteen local browser checks and ten public browser checks pass. Actual public ZIP download, independent extraction, re-import and reload recovery were verified. Six hosting checks pass on each public hostname. Type checking, compiled Worker checks, Windows/Linux CI and the dependency audit pass. [Validation evidence and retained development failures](https://github.com/Simonsbs/presales-solution-workbench/blob/main/VALIDATION.md) are public. ## 4. Manufacturing data quality and traceability demonstrator

**Customer scenario:** A quality team needs to understand inconsistent process data and trace reporting back to the original records.

**Build:** A small ingestion service and SQL data model for synthetic batches, measurements and quality observations. Add completeness checks, duplicate detection, validation rules, lineage, an investigation timeline and an audit trail for reviewed corrections.

**Make it inspectable:** Seed known data defects and show exactly which checks find them. Track reconciliation counts between source and processed records. Include tests for missing measurements, duplicate records, invalid units and unauthorised changes.

**A five-minute demonstration:** Find an anomalous batch, follow the data lineage, review a correction and inspect the audit history.

**Version 1 completion, 11 November 2026:** The standalone application is public without sign-in at [traceability.bestdev.co.il](https://traceability.bestdev.co.il/), with its own [repository](https://github.com/Simonsbs/manufacturing-traceability-demo) and folder `D:\Projects\manufacturing-traceability-demo`. A React investigation workspace uses one TypeScript ingestion/review service with persistent SQLite locally and Cloudflare Worker/D1 publicly. Nine SQL tables retain batch masters, imports, original source rows, current measurements, findings, correction proposals, demo permissions and a hash-linked audit. It checks completeness, duplicates, conflicting readings, types, exact units, ranges, timestamps, equipment and the declared sampling plan. Reviewed corrections update a versioned overlay while preserving the original and resolved finding history. The six-file evidence ZIP includes independently verifiable JSON, source data, measurement/finding/audit CSVs and scope notes. All records and specifications are synthetic; one visitor can switch demo roles, so separate human identity or two-person approval is not claimed.

**Recorded validation:** All 40 unit tests pass. The same 24 HTTP scenarios pass against local SQLite, local Worker/D1, the public hosting URL and the custom domain, with 40 actual requests per final run. Both local runtime processes were stopped and restarted with the same data and access intact. Public D1 retained its complete 14-row, 10-event test workspace and observer access across the evidence deployment. Sixteen local and twelve public browser checks pass, including the actual downloaded ZIP, source JSON re-import, reviewed overlay, retained original, reload recovery and mobile view. All six hosting checks pass on both public origins. Type checking, compiled Worker checks, Windows/Linux CI and the dependency audit pass with zero reported vulnerabilities. [Validation evidence and retained development failures](https://github.com/Simonsbs/manufacturing-traceability-demo/blob/main/VALIDATION.md) are public. Existing root, Knowledge, Integration and Presales sites still return 200. The published portfolio includes Traceability Lab on Home and Projects, with its usage guide and animated architecture board. Project 5 was completed after this release.

## 5. MCP integration and controlled workflow demo

**Customer scenario:** A team wants an AI assistant to investigate operational issues without granting unrestricted access to business systems.

**Build:** A small MCP server exposing a few tools against synthetic records, such as looking up an order, retrieving an error history and drafting an internal follow-up task. Begin with read-only operations. Add one scoped write action with an explicit approval step, input validation and an audit record.

**Make it inspectable:** Test unauthorised requests, token audience and scope handling, malformed tool arguments, denied actions and approved actions. Document the trust boundary between retrieved content and tool instructions. Use the protocol’s [authorization documentation](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/docs/docs/2026-07-28/tutorials/security/authorization.mdx) when choosing the implementation.

**A five-minute demonstration:** Investigate an error, inspect the proposed tool call, refuse an unauthorised request and approve a bounded action against the synthetic dataset.

**Version 1 completion, 11 November 2026:** The independent application is public without sign-in at [workflow.bestdev.co.il](https://workflow.bestdev.co.il/), with its own [repository](https://github.com/Simonsbs/mcp-workflow-demo) and folder `D:\Projects\mcp-workflow-demo`. The official MCP client/server SDK 2.4 negotiates modern protocol 2026-07-28 over Streamable HTTP, with tested legacy stateless interoperability. Four real tools read an order, retrieve untrusted errors, draft a deterministic follow-up and create one explicitly approved synthetic task. A separate review API enforces controller and reviewer scopes. Approval binds the exact payload digest, workspace, actor, resource, order version and expiry. Optimistic SQL commits consume approval, create the task and append the audit atomically; replay returns the existing task. A React workspace exposes the tool schemas, captured protocol bodies, five live denial probes, an injection fixture and a six-file evidence ZIP. SQLite locally and Cloudflare D1 publicly persist bounded workspace documents and hashed capabilities.

**Recorded validation:** All 40 unit tests pass. The same 34 HTTP scenarios pass against local SQLite, compiled Worker/D1, the public provider URL and the custom hostname, with 45 requests per run. Both local processes retain state and access after restart. A complete public checkpoint with one task, three proposals and 28 audit events survives redeployment using its original capability. Twenty local and fourteen public browser checks pass, including all five live denial probes, actual ZIP downloads, independent extraction, evidence re-import, reload recovery and 390 by 844 mobile layout. The final evidence deployment also preserves every original browser workspace field and all 17 previous audit events, with one later replay event retained. Six hosting checks pass on each public hostname, type/build checks and the dependency audit pass with zero reported vulnerabilities, and Windows/Linux [CI](https://github.com/Simonsbs/mcp-workflow-demo/actions/runs/43076383018) passes for the exact deployed commit. [Validation evidence and retained development failures](https://github.com/Simonsbs/mcp-workflow-demo/blob/main/VALIDATION.md) are public. Site version 2 deploys source commit `4ca6f9cd7c602be37662fddd99708d40f7f8e9a9`, with application fingerprint `3e090580a1a8085806d750e8ef7d3d59f930747112856b6b880a9c8a79673cbc`. Manual audience-bound bearer capabilities demonstrate resource and scope handling; this is not an OAuth authorization server, a production multi-agent deployment or vendor certification.
